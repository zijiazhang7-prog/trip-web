## 开场（30 秒）

日记模块我们按「**写入 → 检索 → 推荐 → 互动**」四条链路设计算法：

1. **写入**：正文 Huffman 无损压缩 + 内存索引增量更新  
2. **检索**：标题 Hash/Trie、正文字符位置倒排  
3. **推荐**：兴趣/热度/评分加权 + Top-K 小顶堆  
4. **互动**：浏览量即热度（原子自增）、评分明细聚合、AIGC 分镜脚本  

下面按课设要求的 6 个算法点展开。

## 1. Huffman 无损压缩

**课设要求**：旅游日记压缩存储，核心为无损压缩。

### 为什么选 Huffman

- 日记正文重复字词多（「今天」「景区」「北京」），码点频次差异大，变长编码压缩率高且可逆。  
- 自研 Huffman 包（频次表 + 码表写入包头），便于答辩展示「建树 → 编码 → 解码」全过程；比直接调 gzip 更符合课设算法考查。

### 数据结构

| 结构 | 作用 |
|------|------|
| `Map<Integer, Long>` | Unicode 码点频次表 |
| `PriorityQueue<HuffmanNode>` | 建树用小顶堆 |
| `HuffmanNode` 二叉树 | 叶子=码点，内部节点合并两棵最小子树 |
| `Map<Integer, BitCode>` | 码点 → 变长 01 位串 |
| 自描述二进制包 | 魔数 + 版本 + 原文字节数 + CRC32 + 频次表 + 位流 |

**代码**：`engine/compression/CompressionEngine.java`  
**挂载**：`DiaryServiceImpl.create()` → `compressSafely()` → 字段 `content_compressed`

### 实现流程

```
正文 String
  → codePoints() 按 Unicode 码点扫描（避免中文按 byte 截断）
  → 统计频次 frequencies
  → 小顶堆反复合并 → Huffman 树
  → 递归 buildCodes → 每位码点对应 01 序列
  → BitWriter 写位流 → writePackage（含 CRC32）
  → 存入 BLOB
```

解压：读包头 → 校验 CRC32 → 按树走 0/1 → 还原码点序列 → 拼回 String。

### 复杂度

- 建树：O(k log k)，k = 不同码点数  
- 编码：O(n)，n = 正文码点数  

### 一句话答辩

> 写入时按码点频次建 Huffman 树，高频字短编码，结果带 CRC 存库；读展示仍用明文，压缩主要用于存储优化和算法展示。

## 2. 标题精确查找 — Hash + Trie

**课设要求**：按日记名称精确查询；数据量大、更新快时要高效查找。

### 为什么选 Hash + Trie

- **Hash**：规范化标题作 key，O(1) 精确命中。  
- **Trie**：O(L) 前缀扩展，用户只输入前半段也能召回。  
- 索引不可用时 **回退 MySQL LIKE**，演示不中断。

### 数据结构

- `HashIndex`：`normalizedTitle → List<documentId>`  
- `TrieIndex`：`TrieNode.children: Map<Character, TrieNode>`，叶节点挂文档 ID  
- `AtomicReference<快照>`：全量 rebuild + 原子替换，读路径无锁  

**代码**：`engine/index/IndexEngine.java`、`HashIndex.java`、`TrieIndex.java`  
**业务**：`SearchServiceImpl.searchDiaryByTitle()`  
**接口**：`GET /api/v1/diaries/search/title?title=...`

### 实现流程

```
用户输入标题
  → normalize（小写、去空白）
  → IndexEngine.findExact / findByPrefix → 候选 documentId 集合
  → MySQL：ID IN (...) OR title LIKE
  → 按 heat / rating / latest 排序分页
```

### 复杂度

- Hash 精确：O(1)  
- Trie 前缀：O(L + 命中数)  
- DB 分页：O(pageSize)  

### 一句话答辩

> 标题用内存 Hash 精确命中、Trie 做前缀，命中 ID 再回库过滤排序；索引挂了还有 LIKE 兜底。

## 3. 正文全文检索 — 字符位置倒排索引

**课设要求**：按日记内容全文检索，核心为文本搜索。

### 为什么选「码点位置倒排」

- 中文无空格，不适合英文分词倒排。  
- 按 **Unicode 码点 + 文档内位置** 建 posting，支持任意连续子串（「长城」「博物馆」）。  
- 比全文 LIKE：先锚定首字符，再验证位置连续，候选集更小。

### 数据结构

```text
postings: Map<codePoint, Map<docId, List<position>>>
documentCodePoints: Map<docId, List<codePoint>>  // 增量更新用
```

**代码**：`engine/index/InvertedIndex.java`  
**业务**：`SearchServiceImpl.searchDiaryFulltext()` → `IndexEngine.findByContent()`  
**接口**：`GET /api/v1/diaries/search/fulltext?keyword=...`

### 查询流程 `findContaining(keyword)`

1. 关键词转码点数组 `keywordCodePoints[]`  
2. 取**首字符**的所有 `(docId, startPositions)`  
3. 对每个 `startPosition`，检查第 2…m 个字符是否在 `startPosition + offset` 出现（positions 列表 **二分查找**）  
4. 输出匹配 docId → DB 过滤、排序、分页  

### 增量更新

日记发布/删除时 `DiaryServiceImpl` 调 `IndexEngine.upsert/remove`：写时复制，只重建**受影响码点**的 posting 子表。

### 复杂度

- 查询：O(m + P)，m = 关键词长度，P = 候选位置扫描  
- 增量：O(受影响码点数 × 相关文档数)  

### 一句话答辩

> 正文是码点级位置倒排，查连续子串先锚定首字，再用位置连续性验证，适合中文无分词场景。

## 4. 日记推荐 — 加权评分 + Top-K 小顶堆

**课设要求**：按热度、评价、兴趣推荐；排序算法；不必完全排序，快速取前 10。

### 为什么选 Top-K 堆

- 候选集上限 200 篇（`MAX_CANDIDATE_SIZE`），但课设强调动态数据下快速 Top10。  
- `RankServiceImpl.topK()` 用大小为 K 的 `PriorityQueue`，遍历一遍 **O(n log k)**，不做全表 sort。

### 综合兴趣分（`sortBy=interest`）

```text
score = 0.50 × 兴趣匹配
      + 0.30 × 热度(对数归一化)
      + 0.20 × 评分(归一化到 0~1)
```

- **兴趣匹配**：用户偏好词集（主题/风格/自定义文本分词）与「日记标题 + 正文 + 目的地名」做子串命中，`命中数 / 偏好词总数`  
- **热度**：`log1p(heat) / log1p(maxHeat)`，避免单一爆款碾压  
- **纯热度/纯评分**：直接以 `heatScore` 或 `ratingScore` 作堆键  

**代码**：`DiaryRecommendServiceImpl.java` + `RankServiceImpl.java`  
**接口**：`GET /api/v1/diaries/recommend?sortBy=interest|heat|rating`

### 实现流程

```
loadCandidates() → 最近 200 篇公开日记
  → rankCandidates() 按 sortBy 选评分函数
  → rankService.topK(candidates, scoreFn, k, descending=true)
  → 组装 DiaryVO（用户、目的地、封面媒体）
```

### 一句话答辩

> 兴趣推荐是三因子加权，Top-K 用小顶堆只维护前 K 名，O(n log k)，不对全部日记完整排序。

## 5. 热度 = 浏览量 · 评分聚合

### 热度

- 字段 `heat_score` = 浏览量  
- `getDiaryDetail()` 内 `diaryMapper.incrementHeatScore(id)` **SQL 原子 +1**  
- 前端可叠加本地 bump 展示，统计以 DB 为准  

### 评分聚合

- 表 `diary_rating`：`(diary_id, user_id)` 唯一，重复评分 **UPDATE** 非 INSERT  
- `@Transactional` + `selectByIdForUpdate` 锁日记行 → 更新 `rating_score`（均值）、`rating_count`  
- 分数 1～5，仅公开日记可评  

**代码**：`DiaryServiceImpl.java`、`DiaryRatingServiceImpl.java`

### 一句话答辩

> 热度是详情浏览原子自增；评分是明细表去重加行锁聚合，保证并发下平均分一致。

## 6. AIGC 旅游动画

**课设要求**：根据景点/学校照片生成旅游动画。

### 后端设计

- **输入**：日记 ID + 已落库图片 `mediaList`  
- **Provider 模式**：OpenAI-compatible 多模态 API → 输出 **分镜 JSON**（每幕：mediaId、durationMs、motion、transition、subtitle、narration）  
- 失败降级 mock/template provider  
- 存 `script_json`，**不直接出 MP4**  

### 前端衔接

- `animationPipeline.ts`：后端失败 → 本地分镜模板  
- Canvas Ken Burns 按 `script.scenes` 渲染 WebM  

**代码**：`AnimationServiceImpl.java` · 前端 `src/lib/aigc/`

### 一句话答辩

> AIGC 后端生成分镜脚本，前端按脚本做镜头运动合成视频；后端管结构，前端管渲染。

## 3 分钟压缩口播稿（全讲版）

> 日记模块分四条链路。写入时正文走 Huffman：按 Unicode 码点统计频次，优先队列建二叉树，高频字短编码，带 CRC 的自描述包存进 `content_compressed`；同时 IndexEngine 对正文做倒排增量更新。  
> 检索两条：标题用 Hash 精确加 Trie 前缀，正文用码点位置倒排，查连续子串先锚首字再验证位置连续，索引不可用回退 LIKE。  
> 推荐从 200 篇候选里用加权分——兴趣五成、热度三成、评分两成——配合 RankService 的小顶堆取 Top-K，O(n log k)。  
> 热度是详情浏览原子加一；评分是明细表去重加行锁算均值。AIGC 后端出分镜 JSON，前端 Ken Burns 合成视频。  
> 算法都在 Engine 层，Service 只做编排和事务，符合课设对数据结构选型的要求。

## 助教追问速答

| 问题 | 答法 |
|------|------|
| 为什么不用 gzip？ | 课设要展示 Huffman 建树过程；自描述包含频次表和 CRC，便于验证无损。 |
| 倒排和 Elasticsearch 区别？ | 我们是码点位置倒排，适合作业规模；大规模可换 ES，接口层不变。 |
| Top-K 和 sort 区别？ | n 很大、k 很小时堆更省；我们只维护最差的 K 个再弹出。 |
| 索引怎么更新？ | 日记增删改调 upsert/remove，写时复制受影响 posting。 |
| AIGC 算法在哪？ | 后端 Provider 生成分镜；视频是前端渲染，不是后端 ffmpeg。 |
